## Live integration results and limits

The existing journeys ran against isolated local Identity and School API services on ports 19900/19999, disposable PGlite stores, local-log email delivery and seeded fixtures. No production data or outbound email was used.

The initial web provisioned journey reported **122 OK, 2 NOT OK, 183 N/A**. Its setup depended on a removed `.font-mono` class to retrieve grade/class IDs, aborting the remaining fixtures. Stable `data-entity-id` attributes now identify those configuration rows independently of typography. The expanded rerun then passed student creation and announcement create/deep-link/target/publish workflows, and reached every runnable scenario. It exposed an obsolete educator expectation: the current personal-communications specification and navigation deliberately expose audience-filtered announcements to every selected profile. The test now requires that entry while retaining restricted finance/configuration/calendar checks. Login exceptions also retain actionable diagnostics instead of silently returning false. The final `bun run test:integration:provisioned` rerun passes: **312 OK, 0 NOT OK, 0 N/A**. All setup chapters complete on a fresh disposable tenant. These counts cover the existing runnable matrix; its manual-only modules remain outside the automated run. No additional exclusions or relaxed failure policy were introduced.

Following the user-authorized validation fixes, the complete `melos run test:integration` command passes: **70 API tests, 23 Guardian UI tests, and 17 Teacher UI tests**. The two original inbox HTTP 403 failures were invalid fixtures: staff cannot record system delivery history, and the seeded director has class-scoped send authority. The probe now uses the existing owner fixture to create and publish a unique, guardian-targeted announcement, waits for the notification workflow, and confirms the guardian’s read status with a separate entity read. No grants or school API code changed. `melos run verify` also passes with **106 unit/widget tests**. Existing calendar/student wait helpers remain in place.

## Diff boundaries and release

The initial rebrand production changes are presentation, localization, local assets/fonts, local login pending/visibility state and the public UI flag binding correction described above. The subsequent user-authorized validation work additionally fixes Identity’s response sanitizer: empty JSON-labelled responses retain their redirect/status/headers instead of throwing during JSON parsing. Nonempty JSON still undergoes credential stripping. Identity’s `bun run verify` passes **50 tests**, lint, type checks and builds; both verification redirect regressions were reproduced as HTTP 500 before the fix. A separate real-HTTP check with an in-memory database also passed registration (200), unverified sign-in rejection (403), the emailed verification redirect (302 to `/login?verified=1`), and verified sign-in (200). Authentication clients, registration rules, invitations, route-state implementations, controllers, API bindings, permissions and calculations remain unchanged. Existing operational icons and navigation remain.

Changes remain reviewable in the frontend, mobile and Identity working trees, with no deployment or release signing performed.
